## 全项目审计：原始发现（修复前）

本节保留原始发现、建议和修复前行号，不能作为当前代码仍有这些缺陷的证据。修复状态以文末记录为准。以下均经审阅者源码调用链分析，并由主线程抽查关键写入／错误处理分支。除特别说明外，尚未在桌面应用中动态复现。P1 为应优先处理的可靠性／数据一致性风险，P2 为后续重要缺陷；不是新词元样式引入的问题。

### A1 · P1 · 保存并应用可能部分成功却提示整体失败

- 入口：当前线路编辑器，修改通用配置 TOML 后保存并应用。
- 证据：`src/ChimeraApp.tsx:1362` 先 updateAndActivate/addAndActivate，再于1371行保存片段；`src-tauri/src/commands/config.rs:318` 此时才校验片段；前端1420行 catch仅报“保存失败”。
- 条件：片段 TOML 非法，或第二步片段持久化／同步失败。
- 影响：线路已经保存并激活，界面仍停留旧状态，使用户误以为无变更并重复提交。
- 建议：变更前校验；后端合并事务或明确补偿边界；部分成功时刷新状态并精确提示，不假装整体未提交。

### A2 · P2 · 代理接管时通用配置只更新恢复备份

- 入口：当前线路编辑器，处于自动代理接管状态并修改通用配置。
- 证据：`src-tauri/src/commands/config.rs:348` 调用同步；`src-tauri/src/services/provider/mod.rs:2997` 在存在备份／接管标记时仅 update_live_backup_from_provider后返回。
- 影响：数据库与恢复备份更新，但当前 Live 配置仍旧，仅重启 Codex 不一定生效。
- 建议：更新备份后做接管安全的 Live 同步，保留代理地址和认证占位值；增加代理开启状态下的配置生效测试。

### A3 · P2 · 设置并发保存可能覆盖另一项修改

- 入口：当前设置页，快速点击两个不同开关。
- 证据：`src/views/NewSettingsView.tsx:68` 每次独立读取、合并、整份保存；165行起的开关未串行化；`src-tauri/src/commands/settings.rs:13` 并非通用的字段级补丁合并。
- 条件：两个调用均读取同一份旧快照，然后先后保存不同 patch。
- 影响：后保存的整份快照覆盖前一项修改，两次都可能提示成功。
- 建议：优先后端在锁内字段级更新；至少串行化当前页面保存，补两个开关并发回归。

### B1 · P1 · JSONL 半行可能被永久跳过

- 入口：本机会话自动同步／词元页同步，写入方同时追加会话。
- 证据：`src-tauri/src/services/session_usage_codex.rs:695` 先推进行号，720行解析失败跳过；1203行仍保存 parsed.line_offset；1177行后续按旧游标跳过同一行。
- 条件：读到未完成的末尾 token事件，之后写入方补全同一行。
- 影响：事件可能不再导入，导致用量漏计；不是前端格式化误差。
- 建议：未完成尾行不提交游标，下次重读；增加半行写入后补全原行的回归。审阅者进行了独立内存游标模型验证，未执行真实并发写入测试。

### B2 · P1 · 重建扫描失败可能被当作成功空结果

- 入口：词元页“重建用量”。此行为在本次菜单调整前已经存在。
- 证据：`src-tauri/src/commands/usage.rs:342` 先reset再sync；`src-tauri/src/services/session_usage_codex.rs:610` 缺失目录被跳过，618、644行吞掉遍历错误。
- 条件：已有统计，但源目录缺失、不可读或遍历失败。
- 影响：原统计已清理，重建可能返回成功但为空／不完整。流程先创建数据库备份，因此不应描述为不可恢复的数据丢失。
- 建议：reset前完成来源与可读性检查，传播遍历错误；优先临时导入后原子替换。未修复前，重建前应确认源会话目录可读并保留备份。

### B3 · P1 · 代理换端口失败不恢复旧服务

- 入口：代理配置服务／命令链路；当前简化主界面未挂载高级代理设置页，不能描述为当前页面必然可直接操作的功能。
- 证据：`src-tauri/src/services/proxy.rs:3609` 先存新配置，3624行停止原实例，3637行新实例启动失败直接返回。
- 条件：运行中的代理换到已占用端口等导致启动失败。
- 影响：旧服务已经停止，新配置仍留在数据库，已接管客户端可能指向失效服务。
- 建议：失败时恢复旧配置与服务；新服务成功后再提交接管地址；补端口占用故障注入测试。

### B4 · P2 · MCP 删除后客户端配置残留

- 入口：MCP服务／命令链路；当前简化主界面未挂载 MCP 管理页，不混淆为新词元页面缺陷。
- 证据：`src-tauri/src/services/mcp.rs:104` 先删数据库再同步；314行读取剩余记录，328行只遍历剩余服务器，已删除 ID 不会进入 remove_server_from_app。
- 条件：删除此前已启用且同步到客户端的服务器。
- 影响：数据库中消失并返回成功，但客户端配置还保留该服务器，客户端仍可能启动它。
- 建议：利用删除前快照显式清除受影响客户端的 ID，沿用已有失败回滚机制。审阅者进行了独立内存删除模型验证，未操作真实客户端配置。

## 既有限制与功能建议

- 历史归档只保存日粒度。`usage_stats.rs` 小时分支不读取 usage_daily_rollups，日分支读取；无法精确还原已归档日期的小时明细。当前页只提供今日／近7天／近30天；不应伪造小时分配。建议未来返回粒度／完整性信息，并按可用粒度展示。
- 当前统计API根据时间跨度隐式决定粒度，前端已按同一规则对齐。未来若要跨夏令时始终显示“今日每小时”，宜增加显式粒度协议与带UTC偏移的重复小时标签，而非单改标题。
- 当前新界面不提供自定义历史日期、导出、诊断包和一键恢复入口。这些属于后续可评估功能，不是本次设计要求的遗漏；尤其重建结果可补更直接的备份恢复引导。
- 需要 Rust CI、Windows真实WebView、真实Codex并发写入、权限失败、代理端口占用和备份恢复测试，才能验证上述服务级修复；前端测试不能代替这些验证。
