## 1. 版本定位

v2.5.0 = **可靠性集成版**：A（信任与可恢复性）+ B（管理效率）+ per-model 上游路由，直接跳号 2.5.0（跳过 2.4.7/2.4.8）。

- **A 线（可靠性）**：系统证书链全覆盖、安装事务持久化 + 崩溃恢复、离线安装 + 历史版本 + macOS 运行时、per-model 上游路由。
- **B 线（效率）**：面板搜索 + 批量启停、逐账号用量、导入批处理、OMO/Hermes 路径修正。

## 3. 设计约束

1. **数据库为唯一事实源**：provider、模型路由、OAuth、MCP、Skills、主题的迁移先写备份，再执行版本化迁移。
2. **保持未知字段**：解析 TOML/JSON/JSONC 时保留未知字段，避免上游新增字段在保存时丢失。
3. **迁移可重入**：每个迁移有 schema 版本、事务边界和失败回滚；用量重建是维护操作，不伪装成普通迁移。
4. **不直接覆盖用户配置**：所有写操作先备份。
5. **依赖升级分批落地**：运行时库、用量 parser、代理层和前端批量操作分开提交，便于回滚和定位跨平台问题。
6. **沿用补偿事务**：供应商切换、安装事务等沿用现有 `services/provider/mod.rs` 的补偿回滚模式。

## 4. 分阶段实施（M1–M6）

### M1：依赖审计与升级（前置）

**目标**：先确认当前依赖差异，避免把上游不兼容代码带入。

- 对 `chimera-runtime` / `chimera-platform`（固定 `a5075e6e4d58aad13db259e3eebeabdc0417e3b3`）与 `codex-win-engine` / `codex-theme-engine`（固定 `89b542b9299453dcd833757b10cdb15f6d14d527`）做 API、状态结构、错误类型差异审计。
- 重点：`install_portable_from_msix_with_observer`、`PortableBoundary`、`pause_active_download` / `cancel_active_download`、`restore_previous_install`。
- 固定当前用量样本、安装事务样本、代理脱敏样本和跨平台 CI 产物作为回归基线。
- 建立上游同步矩阵文档 `docs/upstream/sync-matrix-2026-08.md`：逐项记录上游仓库、commit、变更摘要、本地适配说明与不适用理由（沿用 v2.1.0 `cc-switch-v3.19.1-sync-matrix` 的实践）。

**关键文件**：`src-tauri/Cargo.toml`；`chimera-runtime/src/manager.rs`、`codex-win-engine/src/portable.rs`、`codex-win-engine/src/authenticode.rs`（后三者位于固定 rev 的上游 git 依赖内，不在本仓库工作区，须通过依赖升级分支修改）

**验收**：差异矩阵、依赖升级分支、不可直接移植清单、同步矩阵文档。

### M2：系统证书链全覆盖（G1）

**目标**：直连出站与代理隧道统一信任系统证书，覆盖企业 CA / 私有证书环境。

- 主 `HttpsConnector` 与 reqwest client 改用 native certs + webpki 合并（现状：仅 `hyper_client.rs` 的 HTTP 代理 CONNECT 隧道路径合并了 native roots；主路径 `.with_webpki_roots()`，reqwest 走 `rustls-tls` feature 即纯 webpki roots，需切换为 `rustls-tls-native-roots` 或注入统一 root store）。
- 确认所有出站路径（直连、HTTP 代理、SOCKS5、各 provider adapter）走同一条 TLS 配置。
- 增加企业 CA / 私有证书集成测试。

**关键文件**：`src-tauri/src/proxy/hyper_client.rs`、`src-tauri/src/proxy/http_client.rs`

**验收**：企业代理 + 自签 CA 环境下代理全部出站请求正常连接；无证书回归。

### M3：安装事务持久化 + 离线安装 + 历史版本（G2、G3）

**目标**：把 Runtime 管理提升为可恢复的安装事务。

- 接线 `install_portable_from_msix_with_observer` + `PortableBoundary`，持久化安装事务日志到受保护目录。
- 启动时检测未完成事务，自动进入恢复流程（完成或回滚）。
- 新增历史版本目录查询（分页、按平台/架构过滤，支持取消与缓存）。
- 新增安装确认对象：锁定版本、构建、资产、来源、SHA-256、安装路径与自更新策略；后台目录刷新后不得静默改变已确认目标。
- 新增本地离线包导入（`.dmg` / `.zip` / `.msix`）：文件读取 → SHA-256 → 平台签名 → 身份 → 架构 → 版本，全部在安装前完成；离线流程不访问 GitHub。
- macOS 原子替换 + 健康检查 + 失败回滚。
- Windows 支持 MSIX 强制降级与已验证的便携回退；Linux 保持现有包管理路径，不复制 Windows 语义。
- 更新器目标锁定：staging / 暂停 / 恢复继续使用用户最初确认的目标。

**关键文件**：`src-tauri/src/commands/codex_runtime.rs`；`chimera-runtime/src/manager.rs`、`chimera-runtime/src/update.rs`、`codex-win-engine/src/portable.rs`（上游 git 依赖内路径，见 M1）

**验收**：升级中断后重启可恢复；哈希变化拒装；历史版本降级不被静默覆盖；失败安装不替换健康版本；跨架构不误装；v2.4.6 遇到无法识别的未完成事务时有手动清理入口、不阻塞启动。

### M4：per-model 上游路由（G4）

**目标**：在 v2.4.5 已落地的按模型协议探测（`codexModelApiFormats`）基础上，把「按模型选协议」扩展为「按模型选上游」：同一供应商内按模型分流到不同上游 provider/base_url，纳入现有路由事务与回滚。

- Provider 结构新增 provider-scoped per-model route 数据，明确上游 provider/base_url、凭据引用、模型、协议、启用条件；与既有 `codexModelApiFormats` 协议映射统一为一套数据模型，不建第二套平行结构。
- 路由数据纳入现有自动路由事务、model catalog 生成、认证文件写入、回滚快照。
- 前端：Codex 表单模型映射行增加上游线路/协议选择。
- 修复首次启动竞态、反向校验、空模型、重复模型、保存后重载不一致。

**关键文件**：`src-tauri/src/provider.rs`、`src-tauri/src/services/model_fetch.rs`、`src-tauri/src/proxy/providers/codex.rs`、`src-tauri/src/services/provider/mod.rs`、`src/components/providers/forms/CodexFormFields.tsx`、`src/chimeraUtils.ts`

**验收**：同一 provider 可将模型 A/B 分别送往不同 Responses 上游；切换失败完全回滚；新版 Codex 能读取生成 catalog；既有按模型协议探测行为无回归。

## 5. 测试与发布门禁

### 单元与集成测试

- Codex rollout：普通会话、fork、sub-agent、缺父日志、父子 ID 冲突、重复导入。
- Proxy usage：有/无 response id、重试、failover、跨 provider、Chat/Responses/Gemini。

- Catalog：Codex 严格 catalog 字段、Responses/Chat tool schema（`tool_mode`、`web_search` 禁用、namespace 工具抑制）、reasoning、parallel tool call 顺序（保护 v2.4.5/v2.4.6 已落地行为）。

- Install：目标锁定、哈希变化、签名/身份/架构不匹配、中断恢复、失败回滚、MSIX/DMG/ZIP。
- Bulk UI：搜索、批量启停、部分失败、取消、刷新和本地化 key 完整性。

### 跨平台验证

- Windows x64、Windows ARM64、macOS Universal、Linux x86_64。
- GUI 启动与终端 PATH、nvm/fnm/mise、系统证书、企业代理、文件锁和 rename 失败。
- 运行中的 Codex 关闭/重启、更新 staging、降级安装和恢复未完成事务。

### 降级与回滚

- 新增 Provider/路由字段只做加法并保留未知字段，v2.4.6 可安全读取 v2.5.0 的配置与数据库；降级不丢供应商、模型映射与用量数据。
- 数据库迁移带 schema 版本、事务边界与失败回滚；迁移前自动备份，降级步骤写入发布说明。
- 安装事务日志设计为可被后续版本重新接管；v2.4.6 无法识别的未完成事务必须有手动清理入口，不得阻塞旧版启动。
- GitHub Release 保留 v2.4.6 安装包与 updater 元数据回退方案。

### 发布门禁

1. 前端 format、typecheck、unit tests、生产构建通过。
2. Rust fmt、Clippy warnings denied、Rust tests 通过。
3. Candidate 构建验证版本、架构、checksum、SBOM/provenance 和 updater 元数据。
4. 每个安装资产的 SHA-256 与签名绑定关系可重算。
5. 发布说明准确区分 updater 签名、哈希、平台代码签名和公证。
6. 先发布 candidate，再进行旧版本升级/降级/恢复人工验收，最后创建正式 tag。

## 6. 风险与决策记录

| 风险 / 决策 | 对策 |
| --- | --- |
| 本地 `main`（2.4.2）落后 `origin/main`（v2.4.6）12 个提交 | 实施前快进同步并冻结起点 commit（§0.0）；禁止基于 2.4.2 工作区开工 |
| 审计结论随远端演进过时（按模型协议路由已在 v2.4.5 落地即为实例） | §0 已按 origin/main 复核修正；M1 差异审计时对 2.4.3–2.4.6 改动文件二次核对 |
| 上游发布速度快 | 固定 commit、每周差异扫描、人工挑选，不追求实时整仓同步 |
| per-model 上游路由改动大（Provider/认证/回滚） | M4 独立分支，沿用补偿事务模式，先数据模型后 UI；与 v2.4.5 已有协议映射统一，不建平行结构 |
| 依赖升级 API 破坏 | M1 先行，单独提交验证 |
| 历史数据修复改变用户看到的统计 | 自动备份 + 明确提示"重建历史用量" + 保留失败恢复路径 |
| 平台签名现状不一致 | UI 与官网区分 updater 签名 vs 平台代码签名 |
| 版本跳号 2.4.6 → 2.5.0 | 符合"集成版"定位，CHANGELOG 单独成节 |
| **决策：A+B 全做、per-model 上游路由纳入、直接跳 2.5.0** | 一次交付可靠性 + 效率，避免小步发版的反复升级 |
| **决策：先做数据正确性、安全和安装恢复，再做主题市场** | 直接影响信任、可恢复性和发布质量，优先级高于视觉扩展 |
