### M2：协议探测子系统重构（核心）

> 根因总览（编号沿用调研报告 R1–R12；✅ 为主控复核）：
> **R1 ✅** 前端把 默认模型 ∪ 手工映射 ∪ **全部 fetched 模型** 送逐模型探测，任一未识别即阻断保存（`ChimeraApp.tsx:1136-1140, 1161-1170, 1180-1182, 1211-1226, 1470`）；探测结果仅内存，重开编辑器还原 `auto` 每次保存重跑。聚合站必含 embedding/图片模型 → 必失败。
> **R2 ✅** 探测端 `build_api_format_probe_urls`（`model_fetch.rs:869-926`）与转发端 `CodexProvider::build_url`（`proxy/providers/codex.rs:1009-1039`）+ 端点重写（`forwarder.rs:2941` chat→`/chat/completions`、`:3176` anthropic→`/v1/messages`）是两套规则。错配形态：`/anthropic`·`/claudecode` 结尾（探 `/messages`、发 `/v1/messages`）、非 v1 版本段（`paas/v4`、`api/v3` 的 Anthropic 路）、其它自定义前缀（`/api`、`/coding`、`/v2/coding`、`/backend-api/codex`、`/compat`——探测补 `/v1`、转发不补）、`is_full_url`（转发端全协议 POST 原 URL，探测端却探兄弟端点）、base 含 `?query`（`build_url` 字符串拼接成 `…?q=1/responses`）。命中 DeepSeek/智谱/MiniMax Anthropic 基址、Kimi `api.kimi.com/coding`、千帆 `/v2/coding`、aicodemirror、CF `/compat`、`openrouter.ai/api`、火山 `/api/v3`、Azure `/openai`。
> **R3** generic 词表（`:772-789`）缺「参数有误/参数非法/parameter is invalid/invalid input」→ 智谱 1210、SiliconFlow 20015、OpenRouter zod 全 inconclusive；且**先截断 512 字符再分类**（`:47, :597-598`）。
> **R4 ❓** Responses 探针 custom tool 用 `parameters`（`:641-649`），真实形状是 `format`；严格网关报 `Unknown parameter: 'tools[0].parameters'`（无任何 Responses 标记）→ inconclusive → 被降为 Chat 转换。OpenAI 报错顺序需实机。
> **R5** 8 模型并发 × 3 协议（Anthropic 再串行 2 鉴权）峰值 24 并发；429 仅 inconclusive、无退避、逐模型失败原因被 `.ok()` 丢弃（`:392-395`）。
> **R6** 宽松网关忽略非法预算直接生成 → 200 → inconclusive（`:713-719, :739-746`）且**计费**。
> **R7 ✅** Responses 正标记 `"input"`（`:263`）过宽：pydantic `Input should be…`/zod `Invalid input` 必命中 → 只要 `/responses` 路径存在回 400/422 即 strong 且优先选中 → **假阳性**（保存成功、运行时全败）。同类 **A12 ✅**：网关中文报文 `当前模型不支持 Responses API…RESPONSES_MODEL_NOT_SUPPORTED` 负标记全不中（只有带空格的 `not supported` 与 `不支持 responses 能力`），正标记 `responses api` 命中。
> **R8** 诊断丢失：前端三条失败路径（`:1181, :1194-1202, :1216-1225`）无状态码/分类。
> **R9** 运行时自动检测对 UI 线路是死路：前端总写 `wire_api="responses"`（`:1241`）+ 具体 `api_format`（`:1266`），候选条件要求两者皆空（`codex.rs:297-313`）→ 保存期误判永不纠正、失败无运行时兜底。
> **R10** 遗留候选线路 `should_try_codex_chat_auto_fallback` 对 400/404/405/406/415/422/501 **不看响应体**即翻 Chat 并落库（`handlers.rs:867-876, 1120-1130`）。
> **R11 ❓** Anthropic 先 `x-api-key` 后 Bearer，"先校验 body 再鉴权"的网关会误选鉴权字段。
> **R12** `http://` 基址 301 时 POST 降 GET；`/V1` 大写不认（`:1031-1035`）；共享 client 禁自动解压（`http_client.rs:224-227`）遇无条件 gzip 服务器标记全失配；获取模型时默认模型为空取 `result[0]`（`ChimeraApp.tsx:1454`，字节序大写优先→`BAAI/bge-*`）；模板默认模型 `gpt-5.6-sol`（`codexTemplates.ts:42`）第三方站不存在。逻辑死区："三路 generic 拒选"守卫（`:461-467`）永不触发（Responses 不允许 weak）。
> **A2-P1-1 ✅（耦合）** 请求侧按模型协议转换（`forwarder.rs:1192/1198` `_for_model`），**响应侧按供应商默认协议分派**（`handlers.rs:1189/1201` 无 model → `codex.rs:212-214/441` 传 `None` → `codex_api_format_for_model` 跳过 `codex_model_routes`/`codex_model_api_formats` 落 `meta.api_format`）→ 混合目录下 Chat 流被当 Responses 透传给 Codex，或原生流喂进 Chat 转换器报 `Upstream Chat Completions stream ended before sending finish_reason`。**即使探测成功，混合目录在运行时也是坏的。**

**M2a 单一 URL 真相源**
- 抽出 `pub fn codex_upstream_url(base_url, is_full_url, protocol) -> Url`，内部即 `build_url` + `rewrite_codex_responses_endpoint_to_{chat,anthropic}` + `base_url_is_full_endpoint` 现有逻辑（不改转发行为），转发端与探测端共用；`is_full_url` 时只探测末段对应的那一路。
- 顺带修 `build_url` 的 `?query` 字符串拼接（改用 `Url::set_path` 保留 query）；`/V1` 大小写归一。
- 测试：把 R2 真值表全部形态写成 `probe_url == forward_url` 断言。

**M2b 分类器修正**
- 分类前不截断（对 64KB 原文分类，仅诊断串截 512）。
- custom tool 改合规形状 `{"type":"custom","name":…,"description":…,"format":{"type":"text"}}`，保留以继续识别"截断型 Responses 网关"。
- 标记表：Responses `input` 改带边界形式（`'input'`、`"input"`、`input:`、`input[`、`.input`）；generic 正向表补 `参数有误`、`参数非法`、`parameter is invalid`、`invalid input`、`invalid params`；负向表补 `not_supported`、`responses_model_not_supported`、`model_not_supported`、`不支持 responses api`；capability 拒绝改为要求模型语境（`model does not support`、`not supported by/with this model`），且出现 `"param":"max_tokens"`/`unsupported_parameter` 这类"字段被理解"信号时视为**协议证据而非拒绝**（OpenAI gpt-5 Chat `'max_tokens' is not supported with this model. Use 'max_completion_tokens'`）。
- HTTP 200：按响应体形状判 strong（`object=="response"`→Responses、`object=="chat.completion"`→Chat、`type=="message"`→Anthropic），诊断标注 `billable`。
- 429/5xx：尊重 `Retry-After` 单次重试（无头则 1–2s）；模型并发降到 2–4 + 全局信号量；诊断区分 `rate_limited`。
- 删除永不触发的 catch-all 守卫或改为对 Chat+Anthropic 双 weak 且无 strong 时要求用户确认。
- `detect_codex_api_formats` 返回 `{ detected, failures: { model: "HTTP xxx (分类) 原文摘要" } }`；Tauri 命令与 `src/lib/api/model-fetch.ts` 同步。

- 未映射模型策略按 G2：`forwarder.rs:1181-1190` fail-closed → 默认协议 + 首次请求懒探测（复用 M2a/M2b，低并发、结果写回 `codex_model_api_formats`）。
- R10：`should_try_codex_chat_auto_fallback` 改为看响应体协议性证据（复用 M2b 分类器）而非裸状态码；翻转需连续 N 次观察窗口。
- R12：`http_client` 探测路径显式 `Accept-Encoding: identity` 或启用自动解压；`redirect::Policy::none()`（与安全 P3-3 同修）。

## 3. 设计约束

1. **单一真相源**：上游 URL 只允许一个解析函数（M2a）；探测、转发、`/models` 三处共用。任何新增"拼 URL"的代码视为回归。
2. **请求转换协议 == 响应分派协议**：由 `ForwardResult` 显式携带，禁止在 handler 侧重新推断。
3. **探测不计费、失败可解释、结果可持久**：探针必须非生成（若 200 则标 `billable` 并作为强证据一次性使用）；每模型失败原因必须到达 UI；结果落 `meta.codexModelApiFormats` 而非仅内存。
4. **Fail-open with warning 而非 fail-closed**：未映射模型走默认协议 + 懒探测；保存不被探测失败阻断（用户始终可手动选择）。
5. 沿用既有约束：DB 唯一事实源、`toml_edit` 就地编辑保留未知字段、迁移可重入、写前备份、补偿事务；引擎升级不改安装链路语义；宁可失败不可破坏用户文件。
6. **不进产品面**：Pi/多账号 OAuth/预设推广/注入/CDP 远控/插件市场继续在政策外；cc-switch 预设与 UI 改动不采纳（PRODUCT.md "never promotes a provider catalog"）。
7. **CI-only 验证**：本机不做群量构建；每个里程碑以 CI 三平台绿 + 指定实机回归清单为验收。
